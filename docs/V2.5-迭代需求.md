## 2. 核心问题排查思路（第 5、7、8、9 条）

### V25-01（反馈第 5 条）巡检遇阻无响应

**可能原因（按概率排序）**

1. **版本不一致**：线上/本地跑的是 V2.3.4 之前的构建，`blocked` 帧没有 `reason/goal`，前端弹窗逻辑不认。
2. **只提示“已出发”**：`start_patrol` 先发 notice 再逐段规划；第一段就不可达时，`blocked` 已记录但弹窗被下一帧 `state` 覆盖（V2.3.5 修过一次，确认线上是 V2.4.1）。
3. **前端弹窗条件**：`blockedCell` 只在 `frame.data.blocked` 有值时显示；若 `state` 帧里 `blocked` 被清空（如 `_plan_current_segment` 成功但路径为空），弹窗不出现。
4. **巡检根本没开始**：没有巡检点 / 起点在障碍上，只有一条 notice，看起来像“没反应”。

**排查步骤**

```text
① 打开 DevTools → Network → WS，点开始巡检，看有没有 blocked 帧
② 看 state 帧里的 blocked 字段是否非空
③ 若没有 blocked 帧：在后端 start_patrol 打日志，确认第一段规划结果
④ 若有 blocked 帧但没弹窗：检查 App 的 blockedCell 是否被后续 state 帧置空
⑤ 复现“没有巡检点”场景，确认是否只是缺少提示
```

**方案**

- `start_patrol` 第一段规划失败时：立即 `paused=true` + `blocked={cell,reason:"unreachable",goal}`，并广播 `blocked`。
- `state_dict` 的 `blocked` 持久化到弹窗关闭为止，不被普通 state 帧清空。
- 前端：巡检启动后显示“巡检中”进度条；遇到 `blocked` 弹窗，按钮三选一；选“清除”后自动续跑。
- 规划功能本身是生效的（`/api/v1/plan` + 预览卡），需在验收用例里加“规划→出发→遇阻→清除→到达”的完整链路。

### V25-03（反馈第 7 条）电量管理与强制返航

**现状（代码事实）**

- 低于 20% 会自动尝试返航；**返航路径不可达时只记一条异常**，不暂停、不请求人工。
- 电量为 0 时后端进入 `empty` 模式，`move` 会被拒绝；但前端按钮没有禁用，点了只弹一句提示——看起来像“还能操作”。

**方案**

1. **低电量策略**：低于阈值先取消巡检、进入 charging；若返航路径不可达 → `blocked`（reason=`charge_unreachable`），弹窗给两个选项：  
   - “清除 X 处打通返航路线”（扣电，需预算校验）  
   - “人工搬回起点”（调 `carry_home`）
2. **电量保留**：巡检开始前计算“返航所需电量”，低于 `返航电量 + 10%` 不接新任务。
3. **0% 状态**：前端禁用所有控制按钮，只保留“搬回起点”和“查看原因”；后端保持拒绝。
4. 增加“强制返航”按钮（`go_charge`），任何模式可用（除 empty）。

**验收**：把充电点用屏障围死 → 机器人低电量时弹窗要求人工介入，而不是静默耗尽。

### V25-02（反馈第 8 条）假成功提示

**根因（已定位）**

- `resolve_fault()` 的“手动撞墙”分支**免费清障**：不看电量、直接拆格并返回“已排除前方障碍”。
- 前端 `onResolveFault()` 收到 notice 就弹成功 toast，不区分成功/失败。
- 巡检分支调用 `clear_obstacle_at()` 会校验电量；失败时只发 notice，但前端仍按“已执行”提示。

**修复**

1. 后端 `resolve_fault` 统一返回 `{ok, message, cost, cell}`：
   - 免费分支也校验电量（或明确“免费”仅限撞墙第一次）；
   - 电量不足：`ok=false`，不清格，message 写明“需 X%，当前 Y%”。
2. 前端按 `ok` 决定 toast 颜色/文案；失败时不改地图、不关闭弹窗。
3. 加回归测试：电量 1% 时点排障 → 格子不变、提示失败、机器人仍在原地。

### V25-06（反馈第 9 条）按耗电选路

**现状**：A* 的代价 = 几何距离（直行 1、斜行 √2），清障成本只参与“预算够不够”，**不参与选路**。所以会出现“最短但穿金刚石”的路线。

**方案 A（推荐，改动小）**：把清障成本并入边权

```text
进入某格的代价 = 移动代价（0.2 / 0.2×√2）
               + 若该格可清障：该材质清障代价（5 / 2 / 20）
```

- 用 Dijkstra / A* 求“总耗电最小”路径；
- 启发函数用 `octile × 最小移动代价`（可采纳，保证最优）；
- 同一张地图上，最省电路径的总耗电一定 ≤ 最短路路径。

**方案 B（更贴业务）**：双目标

- 先生成 K 条候选路径（Yen / 权重扰动），再按“耗电优先、距离次之”排序；
- 适合以后加“时间/风险”多目标。

**方案 C（产品化）**：UI 提供「最省电 / 最短」开关，默认最省电；预览卡同时显示两个数字，让用户自己选。

**注意**：清障成本是“一次性”的，若路径重复经过同一格需要去重；当前 A* 不会重复访问，可忽略。

## 3. 新需求：LLM 接入（V25-08）设计要点

```text
前端（Agent 面板）
   │  自然语言
   ▼
后端 /agent/command
   ├─ 有 LLM Key：调用云端（OpenAI 兼容），超时 3s
   │     └─ 失败/超时 → 规则解析
   └─ 无 Key：规则解析（现有白名单 10 工具）
         └─ 工具执行前仍做参数校验 + 二次确认
```

- **Key 只放服务端环境变量**（`LLM_API_KEY`），前端永远拿不到；
- 返回体带 `source: "llm" | "rule"`，界面显示“智能模式/规则模式”；
- 限流 + 超时 + 失败降级，避免课堂网络抖动卡死；
- 提示词只允许输出工具 JSON，参数再由后端校验（防越权）。
